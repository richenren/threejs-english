# 儿童英语词汇素材视觉与自动入库规范 V1.1

> 目标：让后续任何新对话/新 Agent 都能按照同一套规则，连续生成词汇图片、自动提交到 GitHub，并让“词库学习馆”无需人工绑定即可直接使用。

## 0. 项目与执行范围

- GitHub 仓库：`richenren/threejs-english`
- 当前开发分支：`feat/local-ai-config-v0.2.1`
- 核心 200 词课程顺序：`frontend/src/game/coreVocabularyOrder.ts`
- 正式图片目录：`frontend/public/vocabulary-assets/`
- 素材清单：`data/vocabulary-assets-manifest.json`
- 图片组件会按单词英文自动寻找同名文件，因此**正常情况下不需要人工维护 word → 图片 ID 映射**。
- 默认按 **10 个单词一批**连续处理。
- 当前已完成前 20 个核心词；新对话开始时仍必须以仓库实际文件和 manifest 为准，不得只依赖此处进度描述。

---

## 1. 目标视觉风格

以项目已确认的参考样式为准：**高质量儿童启蒙 3D 玩具 / 黏土 / 软陶风**。

已确认的整体参考方向包括 apple / elephant / bus，以及仓库中已入库的第一批词汇图片。

核心特征：
- 单个主体居中，儿童一眼可识别；
- Q 版、圆润、可爱，但不能过度变形到难以识别；
- 材质像精致玩具、软陶或磨砂塑料，避免真实照片质感；
- 柔和棚拍光，允许轻微高光与自然落地阴影；
- 背景使用浅色纯色或柔和渐变，不堆叠复杂场景；
- 色彩明快但柔和；
- 最终效果应接近成熟儿童教育产品，而不是普通占位插画或简陋 SVG。

### 1.1 必须保持的风格一致性

新生成图片必须尽量参考已经批准的图片，而不是每次仅靠文字提示重新随机生成。

优先参考：
1. 已批准的项目参考图；
2. 已入库的 apple / banana / orange 等同类型图片；
3. 同一批次前面已经验收通过的图片。

不得因为切换新对话而改变为：
- 写实照片；
- 2D 扁平卡通；
- 黑色描边漫画；
- 高反差影视级渲染；
- 复杂场景插画；
- 风格明显不同的素材合集。

---

## 2. 构图标准

- 输出比例：**1:1**；
- 推荐生成源尺寸：**1024×1024**；
- 正式入库优先使用 **WebP**；
- 主体完整，不裁掉关键结构；
- 主体占画面约 **60%–80%**；
- 四周保留自然留白；
- 视角优先正面或 3/4 正面；
- 图片内部禁止英文、中文、边框、Logo、水印；
- 一个词原则上只有一个明确视觉焦点；
- 需要表达集合、数量、动作、方位时使用专门模板，不要随意添加大量装饰物。

---

## 3. 不同词类的素材规则

### 3.1 具体名词

如 apple / elephant / bus / chair。

采用单体 3D 玩具卡片图，是优先级最高的素材类型。

### 3.2 动物

使用幼态、友好、圆润比例，可适当放大头部与眼睛，但必须保留物种关键特征。

### 3.3 交通工具

采用精致玩具模型感，轮廓清晰。避免道路、城市、人物等复杂背景抢焦点。

### 3.4 家居 / 学习用品

单体展示，保持真实物体关键结构，同时统一玩具材质和圆润边缘。

### 3.5 食物 / 水果 / 蔬菜

优先单体完整展示。只有当切面能显著提高识别度时，才允许“一个完整物体 + 一个切面”的简单组合，例如 kiwi / coconut。

### 3.6 颜色 / 数字 / 形状

优先程序化生成或复用模板，不为每个概念强制生成独立 AI 图片。

### 3.7 动作 / 方位 / 比较概念

使用统一角色或同一物体的可控组合图，不使用随机角色、随机场景的独立插画。

---

## 4. 图片来源策略

采用：**授权明确的互联网素材优先；没有合适素材再生成**。

详细版权策略见：`docs/vocabulary-asset-sourcing.md`。

执行时必须同时满足“版权可用”和“视觉合格”。即使网络图片许可证允许，但风格与项目明显不一致，也不要为了省生成次数强行使用。

优先顺序：
1. Public Domain / CC0；
2. 明确允许项目用途的开放许可证素材；
3. 其他来源明确、许可明确的可复用素材；
4. 找不到合适素材，或风格不一致时，直接生成。

禁止：
- 直接从 Google 图片、百度图片、Pinterest、小红书等搜索结果复制版权不明图片；
- 只因为“看起来合适”就忽略授权；
- 使用带明显水印、Logo、网站标记的图。

互联网素材进入项目时，manifest 必须额外记录：
- `sourceType: "web"`
- `sourceUrl`
- `author`（若有）
- `license`
- `retrievedAt`

生成素材使用：
- `sourceType: "generated"`
- `license: "project-generated"`

## 5. 通用生成提示词

可直接复用以下提示词，并将 `{word}` 替换为当前词：

```text
为儿童英语启蒙应用生成一张高质量词汇卡片素材，主题是“{word}”。

请严格参考项目已经批准的词汇图片风格：精致的儿童 3D 玩具 / 黏土 / 软陶风，
Q版但清晰易识别，造型圆润、柔和、可爱，达到成熟儿童教育产品的视觉质量。

构图：仅一个主要主体，居中展示，主体完整，占画面约 60%–80%，
四周有适度留白，优先使用正面或 3/4 正面视角。

材质与光影：柔和的磨砂玩具或软陶材质，柔和明亮的棚拍光，
允许轻微高光和自然落地阴影，不要强烈明暗对比。

背景：干净的浅色纯色或柔和渐变背景，背景不能出现复杂场景或干扰物。

限制：不要文字、不要水印、不要Logo、不要边框、不要多个竞争性主体，
不要写实摄影、不要恐怖或成人风格、不要复杂装饰。

输出：1:1 正方形，1024×1024。
```

### 5.1 生成时的参考图规则

如果当前工具支持 reference image：
- 至少使用 1 张项目总体参考图；
- 再使用 2–3 张已经批准的同风格素材；
- 参考图仅用于保持视觉语言，不要复制具体对象结构。

对于批量生成，同一批 10 张应使用同一组风格参考，减少批次内漂移。

---

## 6. 负面约束

统一排除：
- photorealistic / documentary photo；
- busy background / clutter；
- multiple competing subjects；
- text / watermark / logo；
- dark horror / aggressive styling；
- metallic sci-fi styling；
- blurry / low detail；
- cropped key body parts；
- 过度拟人导致词义识别困难；
- 与现有素材明显不同的 2D、手绘或扁平图标风。

---

## 7. 验收标准

每张图片入库前至少确认：

1. 不看文字时，成年人和儿童能否快速判断主体是什么；
2. 与已有批准素材目标风格是否一致；
3. 是否只有一个明确视觉焦点；
4. 背景是否足够干净；
5. 是否存在文字、水印、Logo；
6. 缩小到约 200px 后是否仍能清晰识别；
7. 是否适合直接放进 1:1 词汇学习卡片；
8. 是否存在明显畸形、错误数量、错误结构；
9. 若使用网络素材，许可证信息是否完整。

不满足核心条件的图片不得正式入库。应重新寻找或重新生成，而不是提交后再让用户逐张修。

---

## 8. 文件命名与运行时关联规则

正式素材路径：

```text
frontend/public/vocabulary-assets/apple.webp
frontend/public/vocabulary-assets/elephant.webp
frontend/public/vocabulary-assets/bus.webp
```

运行时优先级：
1. `.webp`
2. `.png`
3. `.jpg`
4. 旧版语义 SVG
5. 程序化占位

文件名规范：
- 全部小写；
- 空格和撇号转为 `-`；
- 仅保留 `a-z 0-9 -`；
- 例如 `We'll` → `we-ll.webp`。

只要文件名和单词规范化名称一致，`VocabularyImage` 会自动关联，因此不要为普通词汇额外建立手工映射表。

正式新增素材优先 WebP。推荐单图约 **50–200 KB**；为了保持质量可以适当更大，但不应无控制地把 1024 PNG 原图全部直接提交进仓库。

## 9. “下一批 10 个词”的确定规则

新对话开始后，不能让用户重新告诉你做到第几个词。

必须按以下顺序自动判断：

1. 读取 `frontend/src/game/coreVocabularyOrder.ts`；
2. 读取 `data/vocabulary-assets-manifest.json`；
3. 检查 `frontend/public/vocabulary-assets/` 中实际存在的文件；
4. 按核心 200 词顺序，找出**尚未存在正式图片且 manifest 未 approved** 的前 10 个词；
5. 这 10 个词就是下一批。

仓库文件是唯一可信进度来源。文档中写的“已完成前 20 个”仅用于人类快速理解，若与仓库冲突，以仓库为准。

## 10. 自动生成并提交到 GitHub 的标准流程

用户说“继续”“生成下一批”“放到仓库”等，即表示执行完整链路，而不是只生成预览图。

### Step 1：读取最新分支

目标仓库：
```text
richenren/threejs-english
```

目标分支：
```text
feat/local-ai-config-v0.2.1
```

开始写入前必须获取该分支最新 HEAD，避免基于旧提交覆盖别人的改动。

### Step 2：确定下一批单词

按照第 9 节规则从核心课程列表 + manifest 自动计算下一批 10 个词。

### Step 3：寻找或生成图片

每个词执行：
1. 可合法复用且视觉匹配的网络素材优先；
2. 不满足时使用图像生成工具；
3. 按第 7 节做质量验收；
4. 必要时重新生成。

不得仅生成图片后停止。最终目标是**仓库中出现正式文件**。

### Step 4：转换为仓库正式格式

最终使用规范文件名：

```text
frontend/public/vocabulary-assets/{normalized-word}.webp
```

如果生成工具输出 PNG：
- 优先转换/压缩为 WebP 后再入库；
- 保持 1:1；
- 不要为了压缩造成明显糊图或色带。

如果当前运行环境无法转换，但 WebP 数据已由工具产生，可直接使用 WebP。

### Step 5：二进制图片必须用 Git blob 提交

图片是二进制文件，**不要使用只支持 UTF-8 文本的 create_file / update_file 写图片**。

标准方式：
1. 获取图片二进制；
2. Base64 编码；
3. GitHub `create_blob(encoding="base64")`；
4. 得到每张图片的 blob SHA；
5. 在 `create_tree` 中把 blob SHA 写入对应路径。

10 张图片可以先分别创建 blob，最后一次性创建 tree 和 commit，避免产生 10 个零散提交。

### Step 6：同步更新 manifest

同一批提交必须更新：

```text
data/vocabulary-assets-manifest.json
```

生成图片的标准记录：

```json
{
  "word": "carrot",
  "path": "/vocabulary-assets/carrot.webp",
  "sourceType": "generated",
  "license": "project-generated",
  "status": "approved"
}
```

网络素材必须按第 4 节补全来源和许可证字段。

注意：
- 不允许重复添加同一个 word；
- manifest 中 path 必须与实际仓库文件一致；
- 只有完成质量验收并实际提交文件后，才能写 `status: "approved"`。

### Step 7：一次提交整批

推荐提交信息：

```text
feat(vocabulary): add core word images 21-30
```

流程：
1. 基于最新 HEAD 获取 base tree；
2. 新建 tree：包含本批图片 + 更新后的 manifest；
3. create commit；
4. update branch ref；
5. update_ref 时使用开始阶段读取的 expected HEAD，避免并发覆盖。

如果 expected SHA 冲突：
- 不要 force push；
- 重新读取最新分支；
- 合并/rebase 本批 tree 后再提交。

### Step 8：提交后必须验证

至少检查：
- 第一张图片能从目标分支读取；
- 最后一张图片能从目标分支读取；
- manifest 中能看到本批全部 10 个词；
- 分支 HEAD 已变成新 commit；
- 文件路径正确。

不能在未验证的情况下告诉用户“已经放到仓库”。

### Step 9：检查 CI

提交完成后检查 GitHub Actions：
- 若 still queued / in_progress：明确告诉用户“已提交，CI 正在运行”；
- 若 success：可以说明 CI 已通过；
- 若 failure：查看失败 job，并优先修复由本次提交导致的问题。

不得把“CI 正在跑”说成“已经通过”。

---

## 11. 批量任务的提交原则

为了控制仓库历史和失败范围：

- 默认 **10 张图片 = 1 个 commit**；
- 每批同时更新 manifest；
- 不要 1 张图 1 个 commit；
- 不建议一次生成 200 张后才提交；
- 一批失败时只重做这一批；
- 每批完成后自动继续下一批需要得到用户明确要求；如果用户只说“继续”，默认完成下一批 10 个。

## 12. 新对话 / 新 Agent 的执行指令

用户后续可能只说：

> “继续生成单词图片，按项目里的规则执行。”

此时 Agent 应直接：

1. 打开本文件；
2. 打开 `coreVocabularyOrder.ts`；
3. 打开 manifest；
4. 自动识别下一批未完成的 10 个词；
5. 搜索授权明确且风格匹配的网络图；
6. 没有合适素材则按本规范生成；
7. 自动入库到 `frontend/public/vocabulary-assets/`；
8. 更新 manifest；
9. 提交到 `feat/local-ai-config-v0.2.1`；
10. 验证文件和 CI；
11. 最后只向用户汇报本批词、commit SHA、累计进度和 CI 状态。

**不要要求用户重新上传已确认的风格示例，不要让用户手动下载再上传图片，不要只生成图片但不提交仓库。**
如果当前会话确实无法访问仓库或无法获得已批准的参考图，再明确说明缺少的能力，不得假装已经提交。
